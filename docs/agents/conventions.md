# AI Agent 開發與寫作規範

本文件為 AI Agent 在此專案中進行 Git Commit、Pull Request (PR) 以及 Issue 發佈時的繁體中文撰寫規範。

## 允許的前綴

`init:` `fix:` `adjust:` `review:` `del:` `sync:` `perf:` `revert:` `docs:` `feat:` `style:` `chore:` `refactor:` `test:`

## Commit Message

- 使用繁體中文，簡短明確
- 標題開頭必須使用上述前綴之一；句子開頭不需大寫
- 變數名、函式名、檔案名以反引號（`）包住
- 空一行後以條列補充具體更動

```
feat: 新增 `/notify` 審計紀錄寫入

- 新增 `notify_audit_logs` 資料表與 `AuditService`
- 在 `main.py` 整合 `log_notify` 呼叫
- 新增 `scripts/create_notify_audit_log.sql` 建表腳本
```

## PR 描述

- 標題同 commit：前綴 + 繁中簡述
- 正文第一句說明變更目的
- 空一行後以 `-` 條列主要修改
- 技術名稱同樣使用反引號

```
feat: 新增 API 審計紀錄功能

為 `/notify` 每次呼叫建立資料庫審計紀錄，便於追蹤來源 IP、用量與成功與否。

- 新增 `app/audit_service.py` 與 `app/db_models.py`
- 更新 `app/main.py` 於成功／失敗路徑寫入 log
- 補上 `tests/test_audit_service.py` 單元測試
```

## Issue 撰寫與發佈規範

- 標題與內文一律使用**繁體中文**撰寫。
- 當搭配 `/grill-me`（需求對齊／訪談）流程發佈 Issue 時：
  - **一個 Issue 可以包含多個 Tickets（或 Task 子任務清單）**，將相關的工作項目集中統整於同一個 Issue 中。
  - 正文第一段說明 Issue 的主要背景與目標。
  - 內文需列出 Tickets 清單（建議使用 Checkbox `- [ ]`），明確標示各個子任務的實作範圍。
  - 變數名、函式名、檔案名等技術名稱同樣使用反引號（`）包裹。

```markdown
# feat: 整合 Notification 審計日誌與警報系統

本 Issue 為經由 `/grill-me` 流程對齊後產出的執行規劃，旨在為 Notification 模組建立完整的審計機制與警報發送。

## 主要目標
建立資料庫審計紀錄機制，並在系統發生異常時自動觸發通知。

## Tickets 清單

- [ ] **Ticket 1: 審計日誌資料庫與服務設計**
  - 新增 `notify_audit_logs` 資料表與 `AuditService`
  - 實作 `log_notify` 方法寫入來源 IP 與狀態
- [ ] **Ticket 2: API 整合與錯誤處理**
  - 在 `main.py` 整合 `AuditService` 呼叫
  - 確保成功與失敗路徑皆正確記錄日誌
- [ ] **Ticket 3: 單元測試與說明文件**
  - 補上 `tests/test_audit_service.py` 測試案例
  - 更新 `docs/audit.md` API 文件
```

## 注意事項

- 不要混用英文句子當標題（前綴除外）
- 條列項目描述具體行為，避免「更新程式碼」等空泛用語
- 建立 commit、PR 或 Issue 時一律遵循此格式

## AI Agent 開發行為原則 (Andrej Karpathy Guidelines)

在進行程式碼開發與修改時，AI Agent 應遵循以下 4 大核心行為原則，以降低常犯錯誤、避免過度工程並確保程式碼品質：

### 1. 先思考再寫程式 (Think Before Coding)
**別逕自假設、別隱瞞困惑、主動提出權衡分析。**
- 在開始實作前，明確列出你的假設；若有不確定之處，主動提問確認。
- 若存在多種實現方式或理解歧義，列出不同選項供選擇，不要私下逕行決定。
- 若有更簡單的解法，主動提出建議；若需求有不合理之處，適時提出反駁。
- 遇有不明確之處立即停下，指明不清楚的地方並請求澄清。

### 2. 簡單至上 (Simplicity First)
**撰寫能解決問題的最少程式碼，絕不盲目預留或推測需求。**
- 不添加超出要求的額外功能。
- 不為僅使用一次的程式碼建立不必要的抽象層。
- 不添加未要求的「彈性」或「可配置性」。
- 不為不可能發生的情境編寫過度複雜的錯誤處理。
- 若能用 50 行程式碼實現，絕不寫成 200 行；若顯得過度複雜，應主動重構簡化。

### 3. 精準修改 (Surgical Changes)
**嚴格只動必要的部分，只清理自己產生的廢棄程式碼。**
- 編輯既有程式碼時，不隨意「順便優化」無關的相鄰程式碼、註解或格式。
- 不重構沒有損壞的程式碼與邏輯。
- 嚴格遵守專案既有的程式風格。
- 若發現既有程式碼中存在無關的死碼（dead code），僅需提出說明，不要主動刪除。
- 因本次修改而產生的廢棄 imports、變數或函式，必須隨手清理乾淨。
- **檢驗標準**：Diff 中每一行修改，都能直接追溯回使用者的具體需求。

### 4. 目標導向執行與驗證 (Goal-Driven Execution)
**定義明確的成功驗證標準，持續循環驗證至通過為止。**
- 將模糊的指令轉化為可驗證的目標：
  - 「新增驗證機制」→「針對無效輸入撰寫測試，並確保測試通過」
  - 「修復 Bug」→「撰寫重現 Bug 的測試，修正程式碼直到測試通過」
  - 「重構 X」→「確保重構前後所有測試皆順利通過」
- 對於多步驟任務，主動列出簡要計畫與檢查點：
  1. `[步驟 1] → 驗證: [檢查項目 1]`
  2. `[步驟 2] → 驗證: [檢查項目 2]`
  3. `[步驟 3] → 驗證: [檢查項目 3]`
